Devo reads user config from `DEVO_HOME` and project config from the active
workspace.

## `DEVO_HOME`

`DEVO_HOME` is Devo's user config directory.

| Platform | Default `DEVO_HOME` |
| --- | --- |
| macOS/Linux | `~/.devo` |
| Windows | `C:/Users/your-username/.devo` |

If you set `DEVO_HOME`, the path must already exist and must be a directory.
Devo canonicalizes it before use. If `DEVO_HOME` is unset, Devo uses the
default path and does not require that directory to already exist.

## Files

| File | Scope | Purpose |
| --- | --- | --- |
| `<DEVO_HOME>/config.toml` | User | Main user config for skills, MCP, hooks, tools, logging, updates, and remembered project settings. |
| `<DEVO_HOME>/providers.json` | User | Provider connections, nested model catalog, active model, and credential references. |
| `<DEVO_HOME>/auth.json` | User | Provider API keys and other user-scoped secrets. |
| `<workspace>/.devo/config.toml` | Project | Workspace-level overrides checked when Devo is launched with a workspace root. |
| `<workspace>/.devo/providers.json` | Project | Workspace provider/model overlay. |

Provider API keys should be stored in user-scoped `auth.json`. The matching
`provider.<id>.credential` reference belongs in `providers.json`.

## Precedence

Devo merges config in this order:

1. defaults built into Devo;
2. user config at `<DEVO_HOME>/config.toml`;
3. user provider catalog at `<DEVO_HOME>/providers.json`;
4. project config at `<workspace>/.devo/config.toml`;
5. project provider catalog at `<workspace>/.devo/providers.json`;
6. command-line overrides.

Later sources override earlier sources. This means project config can override
user defaults for one repository, and CLI overrides win over both.

Provider JSON has its own field-by-field merge behavior for provider and nested
model records. User provider JSON is the usual place for connections and
credential references; project provider JSON is best for project-specific
overlays.

## Startup migration

When Devo starts and finds legacy provider/model settings in
`config.toml`, it migrates them automatically before resolving the active
model. User settings move to `<DEVO_HOME>/providers.json`; workspace settings
move to `<workspace>/.devo/providers.json`. Existing JSON values win over the
legacy TOML values.

Legacy API keys are copied to user-scoped `auth.json`, and only their
credential references are written to `providers.json`. Provider-owned TOML
keys are removed after the JSON and credential writes succeed; unrelated
application settings remain in `config.toml`. The migration is idempotent.

## Credentials

The provider record stores a credential reference in `providers.json`:

```json
{"provider":{"deepseek":{"credential":"deepseek_api_key"}}}
```

The actual key is stored in the user-scoped `auth.json`:

```json
{"version":1,"credentials":{"deepseek_api_key":{"kind":"api_key","value":"sk-your-key"}}}
```

If a legacy provider references a missing credential id, Devo fails provider
resolution with an error that names `auth.json`. Do not put `apiKey` or
`api_key` in `providers.json`.

## Inspecting Setup

Run:

```bash
devo doctor
```

`devo doctor` prints the config home, config status, provider status, and model
catalog status. Use it after editing config manually.
