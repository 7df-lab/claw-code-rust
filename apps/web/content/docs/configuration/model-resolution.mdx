---
title: Model Resolution
description: Understand how Devo selects the active provider/model reference.
---

Model resolution turns a user request like `/model
deepseek/deepseek-v4-pro` into a concrete Connection, model id, wire API, and
credential.

## Resolution Order

When a requested model value is present, Devo resolves the `provider/model`
reference against the nested provider/model directory.

When no requested model value is present, Devo checks:

1. the top-level `model` field, if it names an enabled provider/model;
2. the first enabled provider/model in the catalog.

The resolved provider/model entry gives Devo:

- provider id;
- provider-facing model id;
- wire API;
- default reasoning effort.

## Requested Model Sources

A requested model can come from:

- startup CLI `--model`;
- `/model <value>` in the TUI;
- a resumed session's saved `provider/model` reference;
- a direct turn-context override.

`/model` without an argument opens the picker and selects from configured saved
models. `/model <value>` applies the value directly.

## Enabled Versus Configured

Runtime turn selection only uses enabled provider/model entries. Disabled
entries can still be visible to configuration validation so Devo can explain
that a selected model is disabled instead of silently selecting a different
model.

Providers are checked too. If a selected Connection points to a disabled
provider, Devo reports that the provider is disabled.

## Provider Settings

After a provider/model resolves, Devo resolves provider settings:

1. find the provider named by the canonical model reference;
2. confirm the provider is enabled;
3. confirm the model is enabled;
4. confirm the model's `wire_api` is allowed by the provider;
5. read the provider's `credential` reference;
6. resolve that credential id in the user-scoped `auth.json`;
7. merge provider base URL, headers, selected model id, reasoning effort selection,
   context settings, and HTTP proxy settings.

If no provider can be resolved, Devo reports:

```text
No provider configured. Run `devo onboard` to complete setup.
```

## Reasoning Effort Selection

The active reasoning effort selection can come from config or model selection. Devo
stores it as a user-facing value such as `disabled`, `enabled`, `high`, or
`max`, then resolves it into provider-specific request fields for the selected
wire API.

`default_reasoning_effort` on a model record is used when no stronger session or
turn selection is present.

## Request Model Map

For models with variants, Devo builds a provider request model map scoped to the
selected provider. This prevents another provider with the same model id from
changing the wire model name for the active provider.

This matters when a reasoning variant has a different provider-side model name
than the base model.
