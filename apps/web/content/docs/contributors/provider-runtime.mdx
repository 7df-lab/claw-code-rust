This page explains how Devo turns the canonical provider/model catalog into
provider requests.

## Config inputs

Runtime reads the effective `providers.json` catalog:

- `crates/core/providers.json` supplies git-tracked provider templates and model
  metadata;
- user/workspace `providers.json` files add or override Connection and model
  records;
- `provider.<id>.credential` points to a user-scoped `auth.json` credential;
- the selected nested model key is the provider-facing request model id.

The serialized schema is defined in `crates/config/src/provider/catalog.rs`.
The old TOML provider fields are parsed only by the startup migration and are
not a runtime input.

## Resolution

The canonical selection is `provider/model` or `provider/model/variant`. Runtime
validation checks that:

- the provider Connection exists and is enabled;
- the model is enabled;
- the selected wire API is supported;
- the credential reference resolves in `auth.json`;
- arbitrary request/options/headers are valid JSON and can be merged.

If no explicit model is supplied, the top-level `model` is used, followed by the
first enabled model in the merged catalog.

## Router

`crates/server/src/provider_config.rs` builds the provider runtime view. The
provider crate exposes a `ProviderRouter` trait, so server code does not depend
on individual provider implementations.

| Router | Use |
| --- | --- |
| `SingleProviderRouter` | One selected provider route. |
| `MultiProviderRouter` | Multiple enabled provider/model routes, keyed by the canonical model reference. |

The selected route is attached to the turn. This keeps one session on its
intended Connection even when several Connections exist.

## Wire APIs

| Config value | Provider adapter |
| --- | --- |
| `anthropic_messages` | Anthropic-compatible Messages API. |
| `openai_chat_completions` | OpenAI-compatible Chat Completions API. |
| `openai_responses` | OpenAI Responses-compatible API. |

Provider-specific HTTP and streaming behavior belongs in `devo-provider`, not
the TUI or server UI layer.

## Request defaults and variants

Provider, model, and variant records may contain arbitrary `request`, `options`,
and `headers` objects. They are merged from broad to specific:

1. provider;
2. model;
3. selected variant.

`provider/model/variant` selects a named variant without creating another model
identity. Model metadata also carries context limits, capabilities, cost,
release status, reasoning support, and input modalities.

## Dynamic discovery

Native `provider/discover` probes the selected Connection's `/models` or
compatible `/v1/models` endpoint. It normalizes common model metadata and stores
the raw directory entry in the user Connection overlay. The git-tracked
provider template is never modified.

## Web capabilities

Web search and fetch are resolved from model override, provider override, and
global `tools` config, in that order. Modes are `provider`, `local`, and
`disabled`. Local search credentials remain in `auth.json`.

## Validation API

Onboarding and provider editing validate a Connection through Native
`provider/validate` before saving it. The server creates a short-lived route and
attempts a small probe request, catching endpoint, protocol, credential, and
model errors early.
