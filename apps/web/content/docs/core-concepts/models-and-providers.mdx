---
title: Models and Provider Connections
description: Understand provider templates, Connections, models, and variants.
---

Devo uses one catalog to describe provider templates and their models, and a
separate user overlay to record the Connections a user has configured. A model
is owned by its provider, so its stable public identity is `provider/model`.

## Three concepts

| Concept | Meaning | Stored where |
| --- | --- | --- |
| Provider template | Built-in endpoint defaults, supported wire API, and model metadata. | Git-tracked `crates/core/providers.json` |
| Connection | A configured instance of a provider, with endpoint overrides and a credential reference. | User/workspace `providers.json` |
| Model | A provider-facing model id plus optional capability and request metadata. | Nested under the provider in both files |

The API key itself is stored in the user-scoped `auth.json`. `providers.json`
contains only the credential id. A provider template cannot be deleted from the
TUI; disconnecting a Connection removes the user's provider overlay.

## Provider and model identity

Provider ids and nested model ids are map keys. Devo does not require a second
model slug, model name, request model, or description to keep synchronized:

```json
{
  "model": "deepseek/deepseek-v4-flash",
  "provider": {
    "deepseek": {
      "base_url": "https://api.deepseek.com/anthropic",
      "credential": "deepseek_api_key",
      "wire_api": "anthropic_messages",
      "models": {
        "deepseek-v4-flash": {
          "name": "DeepSeek V4 Flash",
          "context_window": 200000
        }
      }
    }
  }
}
```

The nested model key is both the provider-facing id sent in the request and the
second half of the `provider/model` reference. `name` is only a display label.

## Model metadata

Model records can describe context limits, output limits, input modalities,
reasoning controls, sampling defaults, capabilities, cost, release status,
arbitrary request/options/headers, and named variants. The common onboarding
form exposes the useful fields first; Advanced settings exposes the rest.

`small_model` is an optional root selection for lightweight background work,
such as session-title generation. When absent or invalid, Devo chooses a
recognizably lightweight model from the primary provider and then falls back to
`model`.

## Wire APIs

The selected model uses one of these request protocols:

| Wire API | Meaning |
| --- | --- |
| `openai_chat_completions` | OpenAI-compatible Chat Completions API. |
| `openai_responses` | OpenAI-compatible Responses API. |
| `anthropic_messages` | Anthropic-compatible Messages API. |

DeepSeek's official Anthropic-compatible endpoint is represented by a normal
Connection whose `wire_api` is `anthropic_messages`.

## Reasoning and variants

`reasoning_capability` controls the values shown in the picker. A model variant
is selected with `provider/model/variant`; it is not another model identity.
Variant request fields, options, and headers are layered after the model and
provider values. This supports OpenCode-style fast/reasoning variants without
duplicating provider or model records.

## Resolution

For a turn, Devo resolves the explicit `provider/model[/variant]` reference,
checks that the Connection and model are enabled, resolves the credential from
`auth.json`, merges request defaults, and sends the request through the model's
wire API. `/model` and the CLI `--model` use the same reference format.

If no Connection is configured, run:

```bash
devo onboard
```
